# 트러블슈팅 기록

CNC 설비 정상/불량 판별 미니 프로젝트를 진행하며 겪은 에러/이슈를 단계별로 기록한다.
새 이슈가 생기면 아래 표에 행을 추가한다. (참고: `미니 프로젝트 흐름도.png`의 "에러/이슈 정리" 표 형식)

| 발생 단계 | 에러/이슈 내용 | 원인 | 해결 방법 | 예방 대책 |
| --- | --- | --- | --- | --- |
| UI (main.py, 크롤링) | 크롤링이 끝나기 전에 창을 닫으면 백그라운드 스레드에서 `RuntimeError: main thread is not in main loop`가 발생 (`self.after()` 호출부, `main.py`) | `_load_news_worker()`가 백그라운드 `threading.Thread`에서 `self._crawler.fetch_news_items()`가 끝난 뒤 `self.after(0, ...)`로 결과를 메인 스레드에 넘기는데, 그 사이 사용자가 창을 닫아 `self.destroy()`가 먼저 실행되면 Tk 인터프리터가 이미 종료된 상태라 `self.after()` 호출이 실패함 | `_schedule_on_ui_thread(callback, *args)` 헬퍼를 추가해 `self.after()` 호출을 `try/except (RuntimeError, tk.TclError)`로 감쌈 — 창이 닫힌 뒤 뒤늦게 도착한 콜백은 조용히 버림. `_load_news_worker()`가 이 헬퍼를 거쳐 `_show_news`/`_show_error`를 예약하도록 변경 | 백그라운드 스레드에서 Tk 위젯을 건드리거나 `self.after()`를 호출하는 코드는 항상 `_schedule_on_ui_thread()`처럼 방어적으로 감쌀 것. 새 백그라운드 작업을 추가할 때 이 패턴을 재사용 |
| 크롤링 (main.py, 그래프-뉴스 연동) | 그래프 카드를 빠르게 연달아 클릭하면(예: A 카드 → 곧바로 B 카드) 오른쪽 뉴스 패널의 부제목은 B의 검색어인데 실제로 보이는 기사 카드는 A의 결과로 남는 경우가 생김 | `refresh_news()`를 부를 때마다 새 `threading.Thread`가 뜨는데, 두 요청(A/B)이 동시에 진행 중일 때 어떤 스레드의 결과를 반영할지 구분하는 장치가 없었음. 나중에 시작한 B가 먼저 끝나 화면을 갱신해도, 그보다 느린 A의 결과가 뒤늦게 도착하면 `_show_news()`가 그대로 덮어씀(최신/과거 요청 구분 없음) | `self._news_request_id` 카운터를 추가. `refresh_news()`가 호출될 때마다 증가시켜 스레드에 넘기고, 결과가 도착하면 `_apply_if_current(request_id, callback, arg)`가 `request_id == self._news_request_id`일 때만 `_show_news`/`_show_error`를 실행 — 더 최신 요청이 이미 시작된 뒤에 도착한 오래된 결과는 조용히 버려짐 | 같은 백그라운드 작업(크롤링, 향후 모델 예측 등)을 사용자가 짧은 시간에 여러 번 트리거할 수 있는 코드를 새로 추가할 때는, 항상 "이 결과가 아직 최신 요청에 대한 것인가?"를 확인하는 요청 ID/토큰 가드를 같이 넣을 것 |
| 테스트/QA (main.py 백그라운드 스레드 검증) | 위 레이스 컨디션을 재현하는 스크립트에서 `app.update()`를 반복 호출하는 방식으로 기다렸더니, 배경 스레드가 끝나도 `_show_news()`가 전혀 호출되지 않고 스레드가 영영 살아있는 것처럼 보여 "심각한 버그"로 오판할 뻔함 | `threading.Thread` 안에서 부르는 `self.after(0, ...)`는 Tk의 실제 `mainloop()` 이벤트 루프와 맞물려야 안전하게 처리되는데, `mainloop()` 대신 파이썬 `while` 루프에서 `app.update()`를 계속 호출하는 테스트 방식은 이 상호작용을 제대로 흉내내지 못해 콜백이 처리되지 않았음(테스트 하네스 문제였지 실제 앱 버그가 아니었음) | 배경 스레드가 얽힌 동작을 테스트할 때는 `app.update()` 폴링 대신 `app.after(지연, 검증후_app.quit)`을 걸어두고 `app.mainloop()`을 실제로 돌려서 확인하도록 재작성 | Tkinter + `threading` 조합을 테스트할 때는 반드시 실제 `mainloop()`(과 `app.quit()`으로 종료) 기반으로 검증할 것 — `update()` 폴링 결과만 보고 버그라고 단정하지 말 것 |
| 모델링 (`src/classifications.ipynb` 실행 환경) | `jupyter nbconvert --to notebook --execute --inplace src/classifications.ipynb` 실행 시 첫 코드 셀에서 `ModuleNotFoundError: No module named 'sklearn'` — 방금 `pip install scikit-learn xgboost`로 설치했는데도 못 찾음 | 이 저장소는 `venv/`가 이미 있고 `python`/`jupyter` 명령은 `venv/Scripts/`의 것으로 잡히는데, `pip` 명령은 PATH상 `C:\Anaconda\Scripts\pip`를 먼저 찾아 Anaconda 쪽 site-packages에 설치해버림 — 즉 노트북을 실행하는 인터프리터(venv)와 패키지를 설치한 인터프리터(Anaconda)가 서로 달랐음 | `./venv/Scripts/python -m pip install scikit-learn xgboost`처럼 **노트북을 실행할 파이썬을 직접 지정**해서 venv 안에 설치 | 이 저장소에서 새 파이썬 패키지를 추가할 때는 `pip install ...` 대신 `./venv/Scripts/python -m pip install ...`(또는 `python -m pip install ...`)로 설치해 `python`/`jupyter`가 실제로 참조하는 인터프리터와 어긋나지 않게 할 것 |
| 모델링 (`src/classifications.ipynb`, XGBoost 학습) | `XGBClassifier.fit()` 호출 시 `ValueError: feature_names must be string, and may not contain [, ] or <` | 원본 CSV 컬럼명이 `"Air temperature [K]"`처럼 단위를 대괄호로 표기하는데, XGBoost는 내부 DMatrix가 feature name에 `[`, `]`, `<` 문자를 허용하지 않음(반면 scikit-learn의 다른 모델들은 이 컬럼명을 그대로 받아들여 문제 없이 학습됨) | 특성 DataFrame `X`의 컬럼명을 `Air_temperature`처럼 대괄호/공백 없는 이름으로 일괄 rename한 뒤 모든 모델에 동일하게 사용 | pandas 컬럼명을 그대로 XGBoost에 넘기기 전에 `[`, `]`, `<` 같은 특수문자가 있는지 확인할 것 — 원본 CSV 컬럼명을 그대로 쓰지 말고 모델링용으로 한 번 정리된 컬럼명을 쓰는 습관을 들일 것 |
| 환경 설정 (`venv/`→`.venv/` 재구축, 노트북 실행) | `.venv`를 새로 만들고 `./.venv/Scripts/python -m pip install ...`로 패키지도 제대로 설치했는데, `jupyter nbconvert --to notebook --execute`로 노트북을 실행하면 실제로는 **엉뚱한 인터프리터**(예전 `venv/` 또는 Anaconda 베이스)의 패키지로 실행됨 — 에러 없이 "성공"하기 때문에 알아채기 어려움(경고 메시지에 찍히는 `site-packages` 경로를 봐야만 구분 가능) | 이 PC의 PowerShell 프로필이 `conda init` 훅을 포함하고 있어 **새 셸을 열 때마다 `VIRTUAL_ENV`/`CONDA_PREFIX`가 자동 주입**됨. Jupyter의 커널 탐색(`jupyter_core.paths.jupyter_path()`)은 이 환경변수가 가리키는 경로를 실제로 호출한 인터프리터(`sys.prefix`)보다 먼저 검색하고, 기본 `"python3"` 커널의 `kernel.json`이 절대경로가 아니라 `argv: ["python", ...]`(이름만)로 등록돼 있어서 실행 시 PATH에서 "python"을 찾는데 PATH 맨 앞도 같은 이유로 다른 venv를 가리킴. 게다가 `--ExecutePreprocessor.kernel_name=...`/`--NotebookClient.kernel_name=...` CLI 플래그로 강제해도 이 환경에서는 무시되는 별개의 버그까지 겹쳐 있음(PowerShell/Bash 양쪽에서 재현, 원인 미상) | `.venv`용 커널을 절대경로로 명시적으로 등록(`./.venv/Scripts/python -m ipykernel install --user --name cnc-venv --display-name "Python (.venv - CNC project)"` → `kernel.json`의 `argv[0]`이 `.venv`의 전체 경로가 됨), 그리고 `jupyter nbconvert` CLI 대신 `scripts/run_notebook.py`(nbclient를 직접 호출해 `kernel_name="cnc-venv"`를 코드로 못박음)로 노트북을 실행 — PATH/VIRTUAL_ENV/CONDA_PREFIX가 무엇이든 항상 `.venv`가 실행됨 | 이 저장소에서 노트북을 재실행할 때는 `jupyter nbconvert --execute`를 직접 쓰지 말고 `./.venv/Scripts/python scripts/run_notebook.py <notebook>`을 쓸 것. 어떤 인터프리터가 실제로 실행됐는지 확신이 안 서면 출력창 경고문의 파일 경로(`.venv\Lib\site-packages\...`인지)로 검증할 것 |

| EDA (`src/EDA1.ipynb`, `src/EDA3.ipynb`) | `plt.ylabel("고장률")`처럼 세로로 회전된(기본 90도) 한글 y축 라벨이 Malgun Gothic 폰트에서 글자가 깨져(획이 겹치거나 다른 글자처럼) 렌더링됨 — `eda_failrate_by_type.png`(`EDA1`)에서 처음 발견, 새로 만든 `eda3_riskzone_failrate.png`에서도 동일하게 재현 | x축 라벨(L/M/H)이 90도 회전 + Malgun Gothic 조합에서 깨지는 기존 버그(`docs/troubleshooting.md` 위 항목, `EDA1` 8절)와 같은 근본 원인 — matplotlib이 회전된 CJK 텍스트를 이 폰트로 그릴 때 글자가 겹치거나 손상됨. 다만 이번엔 x축이 아니라 y축 라벨이라 `rot=0`(pandas plot 인자)만으로는 고쳐지지 않고 `plt.ylabel()`에 직접 `rotation=0`을 줘야 함 | `plt.ylabel("고장률", rotation=0, labelpad=25, ha="right")`처럼 y축 라벨의 회전을 0으로 강제하고 `labelpad`/`ha`로 눈금과 겹치지 않게 배치. `EDA1`의 `eda_failrate_by_type.png`, `EDA3`의 `eda3_riskzone_failrate.png` 둘 다 이렇게 수정 | 이 프로젝트에서 한글 라벨(x축이든 y축이든)에 회전이 걸리는 그래프를 새로 추가할 때는 항상 `rotation=0`(또는 `rot=0`)으로 우회하고, 저장된 이미지를 실제로 열어서(Read 도구 등으로) 글자가 깨지지 않았는지 눈으로 확인할 것 — 에러 없이 "성공"하기 때문에 코드만 봐서는 알아챌 수 없음 |
## 작성 가이드

- **발생 단계**: 크롤링 / 전처리 / 시각화(EDA) / 모델링 / 평가 / 저장 / 보고서 / UI(main.py) / 테스트-QA 중 해당하는 단계.
- **에러/이슈 내용**: 실제 에러 메시지 또는 증상을 그대로 옮겨 적는다.
- **원인**: 로그·트레이스백을 보고 확인한 근본 원인.
- **해결 방법**: 실제로 적용한 조치 (코드 변경, 설정 변경 등).
- **예방 대책**: 같은 문제가 재발하지 않도록 앞으로 지킬 규칙.
